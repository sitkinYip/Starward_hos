# 登录后主动询问旅途订阅 · 2026-11-19

## 本轮范围与状态

用户将本轮收窄为先完成登录后的授权主动询问；公告展示、关闭和持久化暂缓，待授权完成后再讨论。本轮只增加原生客户端引导，沿用已有账号级旅途订阅 API，不修改服务器、消息分类、投递条件或通知载荷。

实现、固定工具链构建、业务测试、静态检查和本轮直板真机／隔离真实 HTTPS 验收已完成。中间包完成 7 组检查后，导航专项发现切路由期间过早消耗询问记录的问题；修复后使用最终同源签名包完成 3 组复验，不将中间包的 7 组计为最终包复验。本轮尚未提交新的邀请包，计划在公告方案讨论后合包，不将既有邀请或服务器发布记录写成本次新版本已发布。

## 用户流程

普通登录或安全续登进入 `home` 后，先等待既有安装级系统通知许可流程结束，再读取当前账号的 `personal_journey_v1` 订阅。只有服务器明确返回 `revision=0`、`subscribed=false`、`pushEnabled=false`，并且当前环境与账号没有本地主动询问记录时，才展示首次引导。读取失败不解释为默认关闭，也不写入同意。

1. 第一阶段「订阅专属冒险动态？」说明范围是之后分配给本人的新场次、个人剧情来信与关卡动态。点击「订阅旅途动态」才保存 `true / false`；「以后再说」、返回或关闭弹窗不提交订阅。
2. 第一笔写入成功并重新 GET 确认当前订阅后，才进入独立的「接收专属冒险通知？」。点击「接收通知」才保存 `true / true`；「暂不接收」或关闭保留已订阅、通知关闭。
3. 第二笔写入同样等待重新 GET 确认。只有当前权威状态仍为订阅及通知均开启时，才发出一次通知登记同步事件；该事件不请求系统许可。

已有服务器决定不再次主动询问，包括 `revision>0` 的取消、拒绝通知，以及已订阅或已接收状态。设置页独立的旅途订阅、取消和系统通知管理入口继续保留。

系统通知许可、账号旅途订阅和独立通知同意仍是三个不同状态。原有安装级首次许可逻辑未改；新流程没有第二个系统授权请求，既有拒绝不会触发主动重问。系统通知关闭时只说明可稍后到设置开启，明确的手动系统设置入口仍在设置页。

## 状态与隔离边界

| 状态或边界 | 当前实现 |
| --- | --- |
| 隐私、强制改密、身份待确认 | 不取得可询问账号，不展示引导 |
| 后台、导航中、已有目的页、账户或裁剪 Sheet、剧情或来信详情 | 不抢占；取消当前读取并关闭引导，迟到结果不能重开 |
| 本地询问记录 | 按 HTTPS 端点、CA、订阅范围和账号哈希隔离；显示前同步持久化，只表示曾主动询问，不代替服务器同意 |
| 本地记录读取或持久化失败 | 不展示可选引导；设置入口仍可恢复 |
| 退出或切换账号 | 清空引导及其独立订阅源；旧读取、写入或通知事件不能进入新账号 |
| 未确认的网络写入 | 保持原 `requestId`、请求体和发起版本，只有显式「重试确认」才重试 |
| 已保存但回源失败 | 不推进下一阶段；重试只重新读取，不重复已确认写入 |
| 明确 4xx 拒绝 | 回源后仍可选择时恢复明确同意按钮；新选择使用新命令，不陷入只重复 GET 的循环 |
| 409 或历史回执 | 以重新 GET 为准；其他设备已取消时关闭，不覆盖最新决定 |

`PushOnboardingViewModel` 持有引导状态和账号/激活代次；`PushOnboardingPreference` 封装平台偏好。`SliceViewModel` 为引导提供独立的 `onboardingSubscriptions`，避免与设置页订阅区域竞争激活和弹窗状态。页面只传入当前账号、可展示门禁与系统许可状态，不直接读写偏好。

引导由 V2 薄封装 `StarwardPushOnboarding` 使用官方 `PromptAction.openCustomDialog` 展示。沿用原生日夜主题的品牌色、文字层级、圆角与表面令牌，内容可滚动，保存期间禁用同意及拒绝按钮。本轮已实际查看日夜原图；最终包收短的说明「选择会先保存，通知启用后生效。」也已在日间原图核对，无多余断行。未将普通直板机结果扩大为大字号、短窗口或折叠专项适配通过。

## 本轮直板机与隔离 HTTPS 结果

本轮使用专用合成玩家和隔离真实 HTTPS／PocketBase，由主任务独占设备操作。中间包的 `push-onboarding-20261119/verification.json` 记录 7 组成功：登录后主动询问、两次明确同意与独立设置入口；暂不及冷启不重问；提交前 503 的同命令重试及提交后丢响应重放；已有取消决定不重问；后台关闭；第二阶段返回只保留订阅；蒙层关闭不写入并恢复跟随系统主题。这些记录保留为中间包结果。

后续导航检查首次发现进入设置期间，迟到的初始读取可能过早消耗主动询问记录。修复同时核对即时路径深度、转场状态与已有目的页，再冻结最终包。最终 `push-onboarding-nav-20261119/verification.json` 的 3 组结果均通过：

| 最终包复验组 | 实际结果 |
| --- | --- |
| navigation | 延迟 GET 不能覆盖设置页；设置订阅源独立；取消初始读取后回首页仍可主动询问；返回关闭无订阅 PUT |
| finalday | 第一阶段只保存订阅；第二阶段明确「暂不接收」没有第二笔写入；官方冷启后不重问，最终短说明已实际看图 |
| retry | 日夜可读；提交前 503 使用相同命令重试；提交后丢响应以原命令重放，只结算一次 |

最终包及其私有 `signed-hap.json` 将签名与 131 个 ETS 同源结果绑定到上述复验，公开脱敏结果统一见 [设备与 HTTPS 证据](../artifacts/validation/push-onboarding-20261119/device-ui-https.json)。不把 7 组与 3 组相加称为最终包 10 组，也不继承上一轮设置页订阅切片的用例数。

本次手机已有系统通知授权，原有安装级询问逻辑未改；全新系统通知拒绝及其正式分发首次流程未在本轮重验。迟到换账号、持久化失败和明确 4xx／409 冲突等边界由本轮业务测试覆盖，不混写为逐项真机执行。实际 Huawei 投递、订阅分类权益、正式包分发、跨设备与大字号专项仍不由本轮结果证明。
